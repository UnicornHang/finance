## 前端 `sessions/` 接口 500 —— 根因是 vite 代理指向了空端口

**现象**：浏览器 DevTools（localhost:5173/chat）里 `sessions/` 返回 **500**，响应仅 0.2kB、耗时 7ms。

**根因（不在后端）**：
- 后端接口本身完全正常。用 token 直连 VM 的 `GET /api/v1/sessions/` → **200**，能拿到会话列表。
- 真正问题在 **Windows 本机的 vite dev server**（PID 跑 `npm run dev`，`0.0.0.0:5173`）：
  `frontend/vite.config.ts` 里 `target: process.env.VITE_API_PROXY_TARGET || 'http://localhost:8001'`，
  而 **8001 上什么都没有**（`HTTP 000`，backend 已改到 VM 的 8000）。vite 代理转发失败 → 对浏览器返回 **500**。
- 复现命令：`curl -s -w "%{http_code}" http://localhost:5173/api/v1/sessions/` → **500**；修好后 → **401**（后端正常鉴权响应）。

**关键知识点 1 —— vite.config.ts 读不到 `.env` 文件变量**：
`process.env.VITE_API_PROXY_TARGET` 在配置文件阶段是拿不到 `.env` / `.env.local` 的（Vite 是在配置文件解析**之后**才加载 env 文件）。
必须显式 `import { defineConfig, loadEnv }` + `const env = loadEnv(mode, __dirname)`。
否则 `.env.local` 会被静默忽略、代理悄悄回退到默认值 —— 这类 bug 极难排查（不报错，只 500）。

**修复**（2 个文件）：
1. 新建 `frontend/.env.local`（已被 `.gitignore` 的 `*.local` 覆盖，不会提交）：`VITE_API_PROXY_TARGET=http://192.168.8.128:8000`
2. `frontend/vite.config.ts` 改为 `defineConfig(({mode}) => {...})` + `loadEnv`，优先级
   `process.env > .env 文件 > 'http://localhost:8001'`。
   ⚠️ 容器模式无回归：compose 里 frontend 服务显式设了 `VITE_API_PROXY_TARGET: http://backend:8000`，走 `process.env` 分支，仍优先生效。

**验证结果**：改完 vite.config.ts 后 Vite **自动重启**（无需手动杀进程）。
经 5173 代理：登录 200 → `sessions/` 200（4 条会话）→ `POST /chat/stream` **200 SSE 正常流式**。

## 排障方法论（这套以后复用）

「浏览器某个接口 5xx」先分清是**后端**还是**代理**：
1. 直连后端复现：`curl -w "%{http_code}" http://<VM-IP>:8000/api/v1/<path>`
2. 再经前端代理复现：`curl -w "%{http_code}" http://localhost:5173/api/v1/<path>`
3. 两者结果不同 → 问题在 `vite.config.ts` 的 proxy target / 端口，**别去翻后端日志**。

另外：Git Bash 里 curl 传中文 JSON 体容易被编码搞坏（FastAPI 报 `There was an error parsing the body`）；
用 Write 工具落地一个 UTF-8 的 payload 文件，再 `--data-binary @file` 最稳。
Windows 的 python 读不到 Git Bash 的 `/tmp`（映射不同），脚本里写临时文件要用真实 Windows 路径。
